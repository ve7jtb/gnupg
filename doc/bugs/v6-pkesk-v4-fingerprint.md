# Draft upstream report: v6 PKESK writes excess fingerprint bytes for v4 recipients

Status: prepared locally; not submitted upstream.

## Summary

`do_pubkey_enc_v6` in `g10/build-packet.c` advertises a 20-byte recipient
fingerprint for a v4 key but writes the full 32-byte `enc->fpr` buffer.
The extra 12 bytes precede the public-key algorithm identifier. A conforming
parser consequently reads zero as the algorithm in the observed output, and
GnuPG decryption reports `No secret key` even when the recipient key is present.

This occurs when `--allow-9980` encrypts to a v4 ML-KEM-768/X25519 subkey.
The PKESK version (6) and recipient key version (4) are different fields;
a v6 PKESK can carry a v4 recipient fingerprint. The failure does not require
YubiKey, PKCS#11, an external agent, composite signatures, or private keys to
reproduce. No permissive parser workaround is proposed.

## Environment and scope

- Reproduced using stock GnuPG 2.5.24 on macOS ARM64, libgcrypt 1.12.4.
- Independently reproduced in a clean GnuPG 2.5.24 release-tarball build.
- The clean build passes after changing only this serialization operation.
- The same faulty statement is present in the inspected 2.5.23 source; this
  isolated-branch build/result covers 2.5.24 only.
- This report establishes malformed output and an interoperability failure.
  It does not establish a confidentiality compromise or memory disclosure.
- Separate from the mixed-v4/v6 secret-key enumeration issue and from
  `--openpgp` resetting an earlier `--allow-9980` option.

## Standalone reproduction

The patch includes a Python-standard-library-only regression and a synthetic
**public-only** certificate for `gnupg@example.test`. It imports into a disposable
home, disables card access, disables agent autostart and network key lookup,
and uses only public encryption. No private keys or passwords are included.
The fixture was generated by PQ Mail's v4 compatibility certificate encoder;
GnuPG imports and uses its certified algorithm-35 subkey. The test has no runtime
dependency on PQ Mail, Java, or its libraries.

From the source tree, run:

```sh
python3 tests/openpgp/v6-pkesk-v4-fingerprint.py --gpg /absolute/path/to/gpg
```

The test explicitly pins the algorithm-35 subkey with `--recipient FINGERPRINT!`
so the certificate's optional classical encryption subkey cannot be substituted.
It tests both an addressed recipient and `--throw-keyids` as a control.

Before the fix (exit 1):

```text
FAIL v4-fingerprint: algorithm=0, body length=1197 (expected 1185)
PASS anonymous: algorithm=35, body length=1164 (expected 1164)
Invalid PKESK serialization: v4-fingerprint
```

After the fix (exit 0):

```text
PASS v4-fingerprint: algorithm=35, body length=1185 (expected 1185)
PASS anonymous: algorithm=35, body length=1164 (expected 1164)
```

The test checks the PKESK's version, recipient length/version, fingerprint,
algorithm position, total packet length and wrapped-key length. It is a
standalone diagnostic distributed with the source; it is not automatically
part of `make check` and does not add Python to the normal build dependencies.

## Proposed fix

```diff
-      iobuf_write (a, enc->fpr, sizeof enc->fpr);
+      iobuf_write (a, enc->fpr, enc->fprlen);
```

`write_pubkey_enc` already establishes `fprlen` as 20 or 32. The fix makes the
written bytes agree with the immediately preceding advertised length. It
preserves the existing 32-byte v6-recipient behavior and the anonymous path.

## Upstream review notes

The supplied fixture is synthetic and public, with no account/device identifiers
or private material. The patch is based on tag `gnupg-2.5.24`; it contains none
of the experimental adapter or hybrid-signature implementation changes.
Maintainers may prefer porting the diagnostic into the existing Scheme test
harness; the independent script makes the byte-level failure reproducible first.
